# Forecast Persistence

## Purpose
The MeghDrishti project relies on historical weather verification to determine the reliability of the forecast-bust model. However, standard historical APIs (such as Open-Meteo's Archive API) only provide the *actual* historical weather observations. They do not provide the exact historical *forecast* that was issued by our system $N$ days ago.

To solve this, the **Forecast Persistence** layer acts as a local storage mechanism to save the daily forecasts exactly as they were generated by MeghDrishti.

## Timestamps
It is critical to distinguish between the two timestamps stored in each record:
- **`generated_at`**: The exact real-world UTC time when MeghDrishti requested and processed the forecast (e.g., "Right now").
- **`forecast_timestamp` (and `timestamp`)**: The future target time the forecast is *for* (e.g., "Tomorrow at 14:00").

Lead time can later be calculated as `forecast_timestamp - generated_at`.

## Storage Location and Format
The forecasts are stored as a JSONL (JSON Lines) append-only file:
`data/forecast_history/forecast_snapshots.jsonl`

### Schema Example
```json
{
  "location": "Pune",
  "latitude": 18.5204,
  "longitude": 73.8567,
  "forecast_timestamp": "2026-10-05T12:00",
  "timestamp": "2026-10-05T12:00",
  "generated_at": "2026-10-04T12:05:00Z",
  "forecast": {
    "temperature": 30.5,
    "humidity": 65.0,
    "precipitation": 4.2,
    "pressure": 1008.5,
    "cloud_cover": 75.0,
    "wind_speed": 14.0,
    "wind_direction": 210.0
  },
  "bust_probability": 0.72,
  "risk_level": "High",
  "model_version": "SIH-79-MVP-v2"
}
```

## Duplication Strategy
Every time a user visits the dashboard, MeghDrishti fetches the 10-day forecast and runs predictions. To prevent the JSONL file from infinitely inflating with duplicate data on every page reload, the storage service implements a quick deduplication check:
- It maintains a hash set of `location + forecast_timestamp + model_version`.
- If the exact triplet already exists in the file, it skips appending.

## Integration with Verification
In the future, a chron job or verification script (`scripts/prepare_verification_data.py`) will run. It will read `forecast_snapshots.jsonl`, query the Open-Meteo Historical Archive for actuals matching the `forecast_timestamp` (which by then will be in the past), and create aligned `Forecast-vs-Actual` records in `data/verification/historical_data.json`.

**Crucially, we do not fake historical verification data.** The `api/reliability` endpoint will organically become functional only when enough real generated forecasts age into the historical period.
